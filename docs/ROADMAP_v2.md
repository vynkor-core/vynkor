# ROADMAP: Экосистема Veyron & Кайро

> **Два проекта — чёткие границы:**
> - **Veyron** — «тупое» ядро. Маршрутизирует байты, управляет жизненным циклом плагинов. Не знает про AI, не содержит бизнес-логики.
> - **Кайро** — умный плагин поверх Veyron. AI-агент, память, голос. Пользуется ядром как инфраструктурой.

---

## Архитектурный манифест

- Внутри хоста — только UDS. Никаких TCP, никаких Redis, никаких очередей.
- Снаружи хоста — только WebSocket/HTTP через Axum-шлюз (Фаза 4).
- Ядро не знает про AI, не содержит баз данных, не имеет бизнес-логики.
- Плагин не может обойти ядро — он живёт в отдельном процессе и общается только через UDS.
- Протокол — единственный источник истины. Один `.proto` файл, два языка, ноль рассинхронизации.

## Бинарный фрейм (транспортный слой)

Каждое сообщение в UDS-потоке обёрнуто в фрейм:

```
┌──────────┬──────────┬──────────────┬──────────────────────┬──────────┬─────────────────┐
│ Magic    │ Flags    │ Length       │ Target               │ CRC32    │ Payload         │
│ 2 байта  │ 2 байта  │ 4 байта BE   │ 32 байта (UTF-8)     │ 4 байта  │ N байт          │
└──────────┴──────────┴──────────────┴──────────────────────┴──────────┴─────────────────┘
  0xVE 0x52  см. ниже   длина payload  plugin_id или "kernel"  CRC32(payload)  Protobuf
```

**Magic:** `0x56 0x52` ("VR" — Veyron Router). Ядро читает 2 байта — если не совпало,
соединение закрывается немедленно без чтения остального.

**Flags (битовая маска):**
```
Бит 0: COMPRESSED  — payload сжат (zstd)
Бит 1: FRAGMENTED  — сообщение разбито на части (для больших AI ответов)
Бит 2: PRIORITY    — высокий приоритет (системные сообщения ядра)
Бит 3: ACK_REQUIRED — ядро ждёт подтверждения доставки
Биты 4–15: зарезервированы
```

**Target:** идентификатор получателя. Позволяет ядру роутить сообщение без
десериализации Protobuf payload — zero-copy routing по 32 байтам строки.

**CRC32:** считается только от payload. Ядро проверяет при получении —
битый пакет сбрасывается, плагину возвращается ErrorMessage.

**Payload:** Protobuf-сообщение (Envelope из protocol.proto).

> Итого заголовок: 44 байта. Ядро читает их атомарно, принимает решение о роутинге,
> и только потом читает payload.

## Фаза 1: Протокол и MVP-коммутатор 🛠️

**Цель:** сквозной обмен данными Rust ↔ C++ ↔ Python через UDS.
**Критерий готовности:** тестовый плагин подключается, регистрируется, шлёт запрос, получает ответ.

### 1.1 Фиксация протокола (PROTOCOL.md + .proto)

- Зафиксировать бинарный фрейм (44 байта заголовок, см. выше).
- Зафиксировать `.proto` схему (Envelope + все типы сообщений).
- **Это первый артефакт проекта. Без него нельзя начинать кодить.**

### 1.2 Core-Hub на Rust (Tokio)

- Асинхронный UDS сервер (`/tmp/veyron.sock`).
- Чтение фрейма: Magic → CRC32 → route by Target.
- Реестр плагинов in-memory: `DashMap<plugin_id, PluginEntry>`.
- Graceful shutdown: при SIGTERM дать плагинам N секунд на завершение.

### 1.3 Микро-SDK

Три обёртки — минимальные, только упаковка/распаковка фрейма:

| SDK     | Язык   | Для                              |
|---------|--------|----------------------------------|
| veyron-sdk-rs | Rust | Rust-плагины                |
| veyron-sdk-cpp | C++ | C++-плагины (твой друг)    |
| veyron-sdk-py | Python | AI/ML плагины (stt, tts, ai) |

Каждый SDK делает одно: `send(target, message)` и `recv() -> message`.
Никакой бизнес-логики в SDK — только транспорт.

### 1.4 Capability Manifest

`plugin.json` — плагин декларирует что ему нужно до подключения.
Ядро читает манифест и выдаёт только те разрешения, которые разрешены конфигом.

```json
{
  "plugin_id": "weather",
  "version": "1.0.0",
  "permissions": ["network"],
  "events": ["system.ready"],
  "actions": ["get_current_weather"]
}
```

## Фаза 2: Надёжность и Безопасность 🔒

**Цель:** ядро как надёжный менеджер процессов. Плагин не может сломать систему.
**Критерий готовности:** убитый плагин не роняет ядро; перезапускается автоматически.

### 2.1 Менеджмент процессов

- Ядро запускает плагины как дочерние процессы через `tokio::process::Command`.
- Следит за PID, обрабатывает `SIGCHLD`, чистит зомби.
- При смерти плагина публикует `Event { event_type: "system.plugin_died" }`.
- Политика рестарта в конфиге: `always | on-failure | never`.

### 2.2 Watchdog и Health Monitor

- Периодический `Ping` всем зарегистрированным плагинам.
- Нет `Pong` за N секунд → плагин считается зависшим → SIGKILL → рестарт.
- Метрики: uptime плагина, количество рестартов, latency последнего Ping.

### 2.3 Rate Limiter

- На каждый плагин: максимум M ActionRequest в секунду.
- Превышение → `ErrorCode::ERR_RATE_LIMITED` без выполнения.
- Настраивается в конфиге на плагин.

### 2.4 EventStore (at-least-once доставка)

- SQLite таблица: незаквитованные события хранятся до подтверждения.
- Retry worker: каждые N секунд переотправляет pending события.
- После K неудачных попыток → событие помечается `dead` и логируется.

### 2.5 Внешний доступ: WebSocket-шлюз

> ⚠️ Важное уточнение: WebSocket — только для внешних клиентов (мобильные
> приложения, браузер). Внутри хоста — только UDS. Это два разных слоя.

- Axum-сервер принимает WebSocket подключения снаружи.
- JWT-токен строго в query param при хендшейке: `?token=...`.
- Шлюз транслирует WebSocket ↔ UDS. Плагины об этом не знают.
- Защита от Slowloris: таймаут на хендшейк 5 секунд.

### 2.6 CI/CD

- `cargo fmt --check` + `cargo clippy -- -D warnings` в каждом PR.
- Запрет прямых пушей в `main`.
- Интеграционные тесты с mock-плагином на каждый PR.

## Фаза 3: Интеллектуальный слой "Кайро" 🧠

**Цель:** AI-агент поверх Veyron. Кайро — это просто ещё один плагин, только умный.
**Критерий готовности:** голосовая команда → wake word → STT → LLM → TTS → ответ.

### 3.1 Аппаратный сателлит

- Микрофонный массив с аппаратным AEC (эхоподавление).
- LED-матрица MAX7219 для статусов (слушаю / думаю / говорю).
- Связь с хостом через USB HID или отдельный UDS-плагин.

### 3.2 Трёхуровневая загрузка LLM

Динамическая выгрузка/загрузка из VRAM по demand:

| Уровень | Модель              | Режим     | Когда активна                |
|---------|---------------------|-----------|------------------------------|
| Лайт    | ~1B (wake/intent)   | 24/7      | Всегда, слушает триггеры     |
| Средняя | ~7B (chat/vision)   | по demand | Обычные запросы              |
| Тяжёлая | ~30B+ (coding)      | по demand | Сложные задачи, кодинг       |

GPU семафор в ядре не даёт двум плагинам одновременно занять VRAM.

### 3.3 Паттерн Router-Worker

**Диспетчер (Router):** маленькая быстрая модель. Принимает команду,
генерирует строгий JSON-RPC для вызова инструментов. Не болтает — только роутит.

**Собеседник (Worker):** большая модель. Получает результат инструментов,
формирует человеческий ответ, синтезирует речь.

Разделение даёт latency: простой запрос ("который час") обрабатывает только
Диспетчер без загрузки тяжёлой модели.

### 3.4 Долгосрочная память (RAG)

- Изолированный плагин `knowledge` с векторной БД (hnswlib или faiss).
- Само ядро Veyron баз данных не содержит.
- Кайро шлёт `ActionRequest { action: "memory_search" }` → плагин ищет →
  результат идёт в контекст LLM.

## Фаза 4: Масштабирование 💰

**Цель:** выйти за рамки локального хоста.

> ⚡ Фаза 4 — отдельный продукт. Начинать только после стабильной Фазы 3.

### 4.1 Web API (Axum)

- REST + WebSocket шлюз для внешних клиентов.
- Rate limiting, auth, мониторинг через Prometheus.

### 4.2 Маркетплейс плагинов

- Верификация плагина: SHA-256 всего `.zip` архива до распаковки.
- Подпись пакетов: Ed25519 ключ издателя.
- Sandboxing недоверенных плагинов через Linux namespaces.

### 4.3 Облачный инференс (SaaS)

- vLLM кластер для пользователей без GPU.
- API-совместимость с OpenAI (drop-in замена).

## Изменения относительно v1

| Что изменилось | Почему |
|---|---|
| JSON-RPC → Protobuf внутри фрейма | JSON-RPC внутри бинарного конверта даёт сложность без скорости |
| WebSocket явно отделён от UDS | Это два разных слоя, смешение создавало путаницу |
| Filesystem Jail убран из фазы 2 | Процессная изоляция через UDS уже решает это для Rust/C++ |
| SDK разбит на три (rs/cpp/py) | Python нужен для ML плагинов, нельзя игнорировать |
| Фаза 4 помечена как отдельный продукт | Реалистичная оценка объёма для 2 разработчиков |
